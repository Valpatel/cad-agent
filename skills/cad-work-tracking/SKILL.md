# Work tracking: assume the session ends in 30 minutes

Plan as if this session can stop at any moment. Token budgets run out about every 30 minutes, workstations crash,
and disks get reformatted. Anything that exists only in this session's context, in an uncommitted file, in a scratch
or `/tmp` directory, on one machine's disk or in an agent's private memory is lost when that happens. **GitHub is
the record.** A fresh agent on another computer must be able to continue from the issue, the branch and the PR
alone.

## The loop

1. **Find or open the issue first.** Search before opening:
   `gh issue list --state all --search "<words>"`. Open one per piece of work that will take more than a few
   minutes: `gh issue create --title "<outcome, not activity>" --body-file <file>`. Write the body with
   [the template below](#issue-template). A large job gets a tracking issue that links smaller ones.
2. **Branch from the integration branch and push it at once.** Follow the repo's AGENTS.md / CONTRIBUTING.md: in
   cad-agent that is a `feat/<topic>` worktree from `origin/dev`; in a product repo, often `dev`. Push before you
   have much to push (`git push -u origin <branch>`), so the branch exists remotely from the start.
3. **Open a draft PR early** with `Closes #<issue>` in the body: `gh pr create --draft --base <base>`. List in it
   what is still missing. CI on a draft may fail; say why in the PR.
4. **Commit and push in clean chunks.** One coherent change per commit (it builds, its message says what and why),
   pushed right away. Never batch an hour of work into one local commit. Generated files are committed only when
   they are regenerated by the committed sources (no hand-edited exports, no stale evidence).
5. **Checkpoint about every 30 minutes, and before anything long or risky.** A checkpoint is:
   - commit and push everything worth keeping (WIP commits on your branch are fine; say `WIP` in the subject);
   - tick the issue checklist and add a short comment: what changed, what is running, the exact next step;
   - for each run in flight, the host, command, log path and how to collect its results (see `cad-remote-runs`).
   Ask yourself: "if this session ended now, could someone else continue from GitHub without asking me?"
   If not, checkpoint.
6. **Close out as you go.** When a PR merges, its `Closes #N` closes the issue; check that it did, tick the tracking
   issue and comment with the merge commit. Close issues that turned out to be unnecessary, with the reason.
   Delete merged branches and remove their worktrees (after checking no virtualenv imports from them).

## What must never live only locally

- Decisions and their reasons: put them in the issue, the PR description or a doc in the repo.
- Measurements and observations from the user (a photo, "the fan blows up", "it measured 68 mm"): record them
  in the repo (parameters with a note, or a doc) and in the issue, with the date.
- Run configurations and results: the command line belongs in the issue; result files belong in the repo if the
  project tracks them, otherwise attached to the issue or the release.
- Lessons: the repo's `lessons/` (cad-agent) or the product's notes folder, not only an agent's memory file.

Large or licensed inputs (vendor CAD, datasheets) stay out of git; the repo records where they come from and how to
fetch them (a sources list plus a fetch script) so a reformatted machine can rebuild.

## Resuming

At the start of a session, or after a crash, rebuild the state from GitHub before touching anything:

```bash
gh issue list --state open --assignee @me ; gh issue list --state open --limit 30
gh pr list --state open --author @me
git fetch --all --prune && git status -sb && git log --oneline -10 @{u}..HEAD   # unpushed work?
```

Read the tracking issue's latest comment for the next step and the runs in flight; check each run's log on its host
before starting it again (it may have finished). The `cad-resume` agent does this and reports a plan. If local commits
exist that are not on the remote, push them first.

## Issue template

```markdown
<one paragraph: the outcome wanted and why; who asked and when>

**Done**
- [x] <step> (<commit or PR>)

**Next**
- [ ] <step, specific enough to start without asking>

**Running**
- <host>: `<command>`, log `<path>`; done when `<marker>`; collect with `<command>`

**Resume:** branch `<branch>`, PR #<n>. <anything a fresh agent must know first>
```

## Rules that go with it

- Follow the repo's own branch rules: never push to protected branches, never force-push a branch you did not
  create, merge only when the repo's rules allow (CI green, review done, threads resolved, the user's go-ahead
  where the repo requires it).
- Write issue and PR text for a reader who was not in the session: no "as discussed", no chat references.
- Do not post private infrastructure details (host names, addresses, credentials) in public repos. Name a run host
  by role ("the CFD host") and keep its address in the private notes the team already uses.
