# Replacing the placeholder with an engineering engine

Research reviewed on 2026-11-13. This is an integration map, not an installed dependency list. The current kit uses its own editable teaching models. No source from the projects below has been copied into the package, and none is required to open the examples.

The reusable viewer already accepts an external adapter. A calibrated model can replace the placeholder while retaining equipment IDs, system layouts, symbols and controls. Start with [the model interface](./MODEL-API.md), [package integration](./INTEGRATION.md) and the UI package's [viewer contract](../../ui/docs/SYSTEM_FORMAT.md).

## Candidates by problem

| Problem | Primary project and material read | What it contributes | Integration boundary |
| --- | --- | --- | --- |
| Pump, pipe, valve and tank water networks | [OpenWaterAnalytics EPANET](https://github.com/OpenWaterAnalytics/EPANET), including its [pump coefficient implementation](https://github.com/OpenWaterAnalytics/EPANET/blob/dev/src/hydcoeffs.c) | Hydraulic network and water-quality analysis; pump curves, speed settings, closed-pump handling and head-loss coefficients. | Run the hydraulic solver in an external service or a separately tested WebAssembly build. Map node/link results back to stable equipment and connection IDs. A liquid-water network solver does not establish sludge rheology or a gas/steam model. |
| Replaceable centrifugal-pump models and coupled fluid/mechanical systems | [Modelica ControlledPump documentation](https://build.openmodelica.org/Documentation/Modelica.Fluid.Machines.ControlledPump.html) and [Modelica Standard Library](https://github.com/modelica/ModelicaStandardLibrary) | An ideal controlled-flow/pressure pump can later be exchanged for a shaft-driven or prescribed-speed pump with an actual characteristic. Parameters include nominal pressure, mass flow, speed and reverse-flow assumptions. | Keep the Modelica model and its solver outside the UI. Export an FMU where appropriate, or publish solver snapshots through a host adapter. The Standard Library and a Modelica compiler are separate dependencies. |
| Heat exchangers, condensers, pumps, compressors and power cycles | [TESPy documentation](https://tespy.readthedocs.io/en/main/) | Component/connection thermal networks, design and off-design solutions, and examples for Rankine cycles, gas turbines, heat pumps and combined cycles. | A Python backend can solve a configured network after a command or operating-point change. Treat convergence failure as an explicit result; do not present the last converged result as a new solution. A steady operating point is not a transient accident simulation. |
| Fluid properties for thermal calculations | [CoolProp documentation](https://coolprop.org/) | Fluid and mixture properties, incompressible-fluid correlations and water/steam formulations, with multiple language bindings. | Use in a physical model to convert state variables consistently. Property evaluation alone supplies neither a plant topology solver nor a controls model. |
| Substation and electrical-network calculation | [pandapower overview](https://pandapower.readthedocs.io/en/latest/about.html) | Network modelling and power-flow analysis in Python. | Map the electrical graph to a backend network; return bus/branch measurements with explicit units. Keep load-flow results distinct from the kit's normalized energy-flow animation and from generator dynamics. |
| Hosting an exported model using a standard interface | [FMPy current repository](https://github.com/CATIA-Systems/FMPy) and [FMI standard](https://fmi-standard.org/) | FMPy runs Functional Mock-up Units and supports model-exchange/co-simulation workflows. Its current repository lists FMI 1.0, 2.0 and 3.0 support; the older documentation landing page lists fewer versions. | An FMU host owns solver time, initialization and inputs. The browser adapter subscribes to snapshots and translates permitted controls; the SVG renderer never calls the solver. Pin the actual FMU/runtime pair and supported capabilities. |

These choices are candidates for specific physical domains, not interchangeable implementations of every scenario. A brewery may need several models: hydraulics, heat transfer, batch sequencing and a separately supplied fermentation model. Nuclear diagrams in this kit are conceptual heat/circuit demonstrations; selecting a thermal engine does not add neutronics, protection logic or qualified plant behaviour.

## Adapter responsibilities

1. Keep one model session and clock per system. Different layouts subscribe to that session; navigating the viewer must not initialize a second solver or replay old alarms.
2. Map equipment and connection IDs explicitly. Preserve separate fluid circuits and AC/DC/mechanical/thermal domains. A visual crossing is not a connection; a heat exchanger must not merge its two fluids.
3. Carry physical measurements and units separately from visual percentages. For example, preserve a measured mass flow in kg/s, then compute a bounded visual flow fraction against a documented design range. A 75% animation is not a claim of 75 kg/s. Keep raw values available to equipment metrics and trends.
4. Validate every command before changing solver inputs. Map a UI valve-opening command to the intended actuator variable; model commands, fault experiments and maintenance actions should remain distinct.
5. Publish time, model identity, configuration revision, measurement validity and convergence status. Unavailable measurements should render as unavailable; they must not silently become zero. A disconnected display should retain an explicit stale/invalid state.
6. Preserve a resumable session only when the solver supports it. Otherwise label an export as configuration/results, not an exact restart. Include engine version, model hash, units and initialization assumptions in its provenance.
7. Keep output deterministic where the engine permits, and record seeds for synthetic incidents. Do not add random damage or sound events inside renderers.

## A practical first integration

For a pump demo, start with one reservoir, a pump curve, a valve, a receiving tank and declared pipe resistance. Provide the actual curve, nominal speed, fluid properties, elevations and pipe dimensions as editable input data. Compare zero speed, closed valve, normal flow and a changed speed against the upstream solver's own example or reference result before connecting animation. Then verify that two viewer layouts show the same state and that pause, reset, import and command rejection behave coherently.

For power examples, begin with a small pandapower network for static electrical results or a TESPy cycle for thermal operating points. Preserve the existing illustrative engine as an explicitly selectable teaching model; show the external engine's identity and limitations alongside its results. Integration should add physical meaning without changing the viewer's public rendering API.
